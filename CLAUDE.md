# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Бот для мессенджера [MeshCore](https://github.com/meshcore-dev/MeshCore) — подключается к устройству по USB в режиме компаньона, слушает сообщения в каналах и прямые сообщения, отвечает на команды (`/ping`, `/help`, `/weather`, `/weathernow`, `/weather2`, `/traffic`, `/rate`, `/ver`, `/moon`, `/mercury`).

## Команды разработки

```bash
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env           # затем задать MESHCORE_PORT
python bot.py                  # запуск бота
```

Автоопределение USB-порта устройства:
```bash
python find_device.py
```

Отладка — просмотр всех сырых событий от устройства:
```bash
python scripts/debug_bot.py
```

Формального test-раннера/линтера в проекте нет (без pytest/ruff в requirements.txt). `scripts/test.py` и `scripts/test_send.py` — ручные скрипты для проверки конкретного поведения через реальное/эмулируемое устройство, а не unit-тесты в обычном смысле.

Docker:
```bash
docker-compose up -d           # порт задаётся через MESHCORE_PORT в .env
```

## Архитектура

Точка входа — `bot.py`, `async def main()`. Обработка команд вынесена в `core/`.

### Переподключение к устройству

- В начале каждой сессии, сразу после DEVICE_QUERY, `sync_device_clock()` выставляет часы ноды по компьютеру (`set_time`): нода без RTC после перезагрузки ведёт время с прошлой даты, а по нему ставит метки своим advert'ам (узлы, слышавшие advert с более поздней меткой, отбрасывают такой как повтор) и `lastmod` контактам. Прошивка переводит часы только вперёд — меньшее время отвергает с `ERR_CODE_ILLEGAL_ARG`; тогда в логе предупреждение, а не ошибка.
- `main()` — только цикл переподключения: `load_settings()` (env → `config`) один раз, затем `open_device()` → `run_bot()` → `close_device()`. `run_bot()` — одна сессия работы с конкретным `mc`: инициализация (DEVICE_QUERY, каналы, контакты) и `asyncio.gather()` всех корутин.
- Обрыв COM-порта (выдернули USB, устройство перезагрузилось) библиотека сообщает событием `DISCONNECTED` — `run_bot()` на него подписан, отменяет все корутины сессии и бросает `DeviceDisconnected`. Встроенный `auto_reconnect` библиотеки не используется: он переоткрывает порт, но не повторяет инициализацию бота (DEVICE_QUERY с версией 3 прошивка держит только до перезагрузки, секреты каналов, контакты).
- После обрыва — пауза `RECONNECT_DELAY_SECONDS` (env, по умолчанию 15 c) и новая сессия с нуля; неудачное открытие порта повторяется до `RECONNECT_ATTEMPTS` (env, по умолчанию 10) раз подряд с той же паузой, после чего `sys.exit(1)`. Оба значения — целые >= 1, иначе умолчание с предупреждением; прочитанные значения печатаются в лог при старте. Счётчик сбрасывается при каждом успешном подключении. Тот же лимит действует и на самый первый старт. Всё состояние сессии (`route_cache`, дедупликация) при перезапуске теряется; состояние шедулеров переживает его за счёт файлов `*_last_*.txt`.

### Поток обработки сообщения

1. Главный цикл в `main()` крутит `asyncio.wait(FIRST_COMPLETED)` на двух событиях: `CONTACT_MSG_RECV` (личка) и `CHANNEL_MSG_RECV` (канал).
2. `process_message()` разбирает payload:
   - В каналах текст приходит в виде `"Имя: /команда"` — парсится по первому `:` на `sender` и `text`.
   - Дедупликация по ключу `"{source_key}:{sender_timestamp}:{text}"` в множестве `processed_messages` (растёт неограниченно в рамках процесса).
   - Для личных сообщений перед фактическим ответом отправляется пустой ACK (`mc.commands.send_msg(source_key, "")`).
3. Команда диспетчеризуется через `core/commands.py::dispatch()` → `core/commands.py::Context` собирает всё нужное состояние (текст, hops, route_data, api key, config, сам `mc`).
4. Ответ (если не `None`) прогоняется через `to_lat()` (замена кириллических омоглифов на ASCII для экономии байт при передаче по LoRa) и режется на части `split_msg()` (`core/msgsplit.py`) по границе слов с лимитом байт (130 байт в каналах, 150 в личке — у LoRa маленький MTU).
5. Отправка частей ответа идёт с `time.sleep(2.0)` между сообщениями (не `asyncio.sleep` — специально блокирующий, чтобы не заспамить радиоэфир).

### Маршруты и хопы (`route_cache`)

- Событие `RX_LOG_DATA` подписано отдельно (`on_rx_log`) и параллельно с основным циклом собирает пути пакетов в два хранилища (записи не старше 30 секунд): `route_by_hash: dict[msg_hash]` — только канальные сообщения, которые библиотека смогла расшифровать, и только **первая** услышанная копия (в том числе с пустым путём — услышано напрямую): событие сообщения прошивка создаёт именно по первой копии, а следующие — эхо ретрансляторов, и раньше каждое такое эхо перезаписывало путь, так что `/ping` показывал путь эха, а не тот, которым сообщение пришло; `route_cache: list` — текстовые сообщения (`GRP_TXT`=5 и `TEXT_MSG`=2) с непустым путём, у `TEXT_MSG` вдобавок однобайтовые хэши получателя/отправителя (первые два байта `pkt_payload`). Прочие типы (ADVERT, ACK, PATH…) в `route_cache` не кладутся — иначе подбор по времени подхватывал путь эха собственного advert'а бота.
- Поиск маршрута: сначала точно по `txt_hash` события в `route_by_hash` (есть только в формате `CHANNEL_MSG_RECV_V3` — прошивка шлёт его, только если клиент объявил протокол v3 командой `DEVICE_QUERY`; бот делает это при каждом старте, прошивка помнит версию до перезагрузки). Иначе — по времени среди записей `route_cache` своего типа (для лички — ещё и с совпадением хэшей получателя-бота и отправителя-`pubkey_prefix`), в два шага: (1) по времени прихода — самая свежая запись, пришедшая не раньше чем за 3 с до события (RX_LOG того же пакета опережает событие на ~15 мс; `recv_time` — по часам компьютера, не ноды) и с тем же `path_len`, что у события; (2) если не нашлось — прежний подбор по `abs(sender_timestamp - recv_time) <= 7`. Первый шаг нужен потому, что `sender_timestamp` — часы отправителя (у нод без RTC сбиты на секунды-минуты) и время *создания* сообщения: личка, сначала отправленная по прямому маршруту и переотправленная flood'ом после неудачи, приходит с `sender_timestamp` на 15+ с раньше прихода.
- Личное сообщение библиотека в RX_LOG не расшифровывает (шифр пары узлов), поэтому для лички — только подбор по времени. Причём по прямому маршруту (`DIRECT`, отправитель уже знает путь) каждый ретранслятор вычёркивает себя из пути, и пакет доходит с пустым `path` при любом числе хопов — маршрут такой лички из пакета не восстановить. Путь есть только у flood-лички.
- `path_len == 255` в payload личного сообщения означает «доставлено прямой маршрутизацией», а не 0 хопов и не 255 хопов; реальное число хопов в пакете при этом неизвестно.
- `core/echo.py` логирует, какой ретранслятор услышал **любую** передачу бота («📡 Ретранслятор услышал …», с путём, SNR/RSSI и задержкой от отправки). `track_own_sends(mc)` вызывается в `run_bot()` до запуска корутин и оборачивает `send_chan_msg`/`send_msg`/`send_advert` у `mc.commands` — поэтому ловятся отправки всех модулей (ответы, шедулеры погоды/пробок/версий), и новым модулям ничего делать не нужно. Своя передача в RX_LOG не попадает, так что услышанный пакет бота — всегда ретрансляция; отсутствие эха недоставку не доказывает. Опознание: канал — `sender_timestamp` + текст `"ИмяБота: …"` + непустой путь; личка (не расшифровывается) — однобайтовые хэши отправителя-бота и получателя в начале `pkt_payload`, путь может быть пустым (прямой маршрут), и ACK с ответом одному получателю по эху не различить; advert — по ключу бота, только flood (zero-hop не ретранслируется). Помнит отправленное 60 с. `on_rx_log` в `bot.py` пропускает такие пакеты через `own_sends.match()` — в `route_cache` им не место.

### Команды (`core/commands.py`)

- `COMMANDS: dict[str, Callable]` — реестр команд, ключ — строка команды (`"/ping"` и т.п.). Чтобы добавить команду: написать `async def _foo(ctx: Context) -> str | None` и зарегистрировать в `COMMANDS`.
- `dispatch()` возвращает `None`, если текст не начинается с `/` или команда не найдена — тогда бот молчит.
- Хендлер может сам отправить сообщение через `ctx.mc.commands.send_chan_msg(...)` и вернуть `None` (см. `_weathernow`), либо просто вернуть текст для отправки вызывающей стороной.
- `/test` — служебная команда, не задокументированная в README как пользовательская. Возвращает длинную строку специально для ручной проверки `split_msg()` (разбиение ответа на части под лимит байт LoRa).

### Погода — три независимых источника

- `core/weather.py` — OpenWeatherMap (нужен `OPENWEATHERMAP_API_KEY`), используется командами `/weather` и `/weathernow`, а также фоновым `weather_broadcast_scheduler()` (крутится параллельно с `listen()` через `asyncio.gather()` в `main()`, ждёт до заданного `WEATHER_HOUR:WEATHER_MINUTE` в часовом поясе `WEATHER_TIMEZONE_OFFSET` и шлёт прогноз в `WEATHER_CHANNEL_IDX`).
- `core/openmeteo_omsk.py` — Open-Meteo (без ключа), используется командой `/weather2`. Через геокодер Open-Meteo резолвит произвольный город; для «Омск» использует захардкоженные координаты.
- `core/gismeteo_omsk.py` — HTML-скрапер Гисметео (requests + BeautifulSoup), **не подключён ни к одной команде** — самостоятельный модуль, хрупкий к вёрстке сайта.

### Мост с Telegram (`core/telegram_bridge.py`)

- Опционален: включается, только если заданы все три `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_CHANNEL_IDX`. Схема жёстко «один чат ↔ один канал MeshCore», без whitelist пользователей внутри чата и без поддержки нескольких пар.
- `telegram_bridge(mc, config)` — отдельная корутина, крутится через `asyncio.gather()` в `bot.py::main()` наравне с `listen()` и `weather_broadcast_scheduler()`.
- **Telegram → MeshCore**: long polling `getUpdates` (raw HTTPS через `aiohttp`, без сторонних Telegram-библиотек — по аналогии с `core/weather.py`/`core/traffic.py`). Сообщения не из `TELEGRAM_CHAT_ID` игнорируются. Текст прогоняется через тот же `core/commands.py::dispatch()`, что и обычные сообщения бота (значит, `/ping` и другие команды, отправленные из Telegram, работают как обычно); если это не команда — пересылается как `"{sender}: {text}"`. Результат идёт через `to_lat()` + `split_msg()` и `mc.commands.send_chan_msg()` с тем же `time.sleep(2.0)` между частями, что и обычные ответы.
- **MeshCore → Telegram**: не отдельный цикл — встроено в `process_message()` в `bot.py`: если сообщение пришло в `TELEGRAM_CHANNEL_IDX`, оно асинхронно (`asyncio.create_task`) уходит в Telegram через `send_to_telegram()`.
- **Защита от зацикливания эха**: оба направления отправки в один и тот же MeshCore-канал (обычные ответы бота из `process_message()` и сообщения, слетающие туда из Telegram-моста) регистрируют отправленный текст в общем `config["_own_channel_echoes"]: dict[text -> send_time]` (TTL 60 c). Приходящее сообщение с текстом из этого словаря не пересылается в Telegram повторно. Это единственный канал связи состояния между `bot.py` и `core/telegram_bridge.py` — оба модуля читают/пишут в один и тот же передаваемый `config`, а не импортируют друг у друга внутреннее состояние.

### Чтение чужого Telegram-канала (`core/telegram_userfeed.py`)

- Отдельная фича от `core/telegram_bridge.py` — решает другую задачу: `telegram_bridge` требует, чтобы бот был участником чата (работает через Bot API), а `telegram_userfeed` читает **любой публичный канал**, куда бот не добавлен, авторизуясь как обычный Telegram-пользователь (Telethon, протокол MTProto). Только приём: в исходный канал бот не пишет.
- Опционален: включается, только если заданы все четыре `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SOURCE_CHANNEL`, `TELEGRAM_USERFEED_CHANNEL_IDX`.
- `TELEGRAM_API_ID`/`TELEGRAM_API_HASH` — данные Telegram-приложения с https://my.telegram.org/apps, это **не токен бота**, а credentials для user-аккаунта.
- Перед первым запуском `bot.py` нужно один раз выполнить `python scripts/telegram_login.py` — интерактивно запрашивает номер телефона и код подтверждения, сохраняет сессию в файл `TELEGRAM_USER_SESSION` (по умолчанию `telegram_user.session`). Без этого файла `telegram_userfeed()` не сможет авторизоваться (интерактивный ввод внутри самого бота не предусмотрен — несовместимо с фоновым/Docker-запуском).
- `telegram_userfeed(mc, config)` — отдельная корутина, крутится через `asyncio.gather()` в `bot.py::main()` наравне с остальными. Подписывается на `NewMessage` в `TELEGRAM_SOURCE_CHANNEL` через `client.on(...)`, а не polling — Telethon сам держит сессию через `run_until_disconnected()`.
- Сообщения пересылаются как есть (`"{sender}: {text}"`), **не** прогоняются через `dispatch()` — это чужой контент, а не команды пользователя боту.
- Типовое применение — оповещения МЧС Омской области об угрозе БПЛА: `TELEGRAM_SOURCE_CHANNEL=@mchs_omsk`, `TELEGRAM_USERFEED_CHANNEL_IDX` указывает на отдельный канал тревог (не общий инфо-канал), чтобы люди могли подписаться конкретно на тревожные оповещения. У МЧС/РСЧС нет официального API для этих оповещений — их публичный Telegram-канал единственный практичный программный источник.

### Прочее

- `core/traffic.py` — команда `/traffic`, скрапит балл пробок Омска с ngs55.ru регуляркой по HTML. Также фоновый `traffic_broadcast_scheduler()` (крутится параллельно с `listen()` через `asyncio.gather()` в `main()`, стартует с задержкой 5 c по аналогии с `advert_scheduler`) с интервалом `TRAFFIC_INTERVAL_MINUTES` (значение зажимается снизу до 5 минут; `0` отключает проверку целиком) опрашивает балл пробок и шлёт отчёт в `TRAFFIC_CHANNEL_IDX`, только если балл изменился по сравнению с прошлой проверкой — это отделяет частоту опроса сайта от частоты сообщений в канал. Последний известный балл хранится не только в памяти (`last_score` внутри цикла шедулера), но и в файле `traffic_last_score.txt` в корне проекта (не в git, см. `.gitignore`) — читается при старте и перезаписывается при каждом обнаруженном изменении, чтобы рестарт бота не воспринимал текущий балл как «изменение с нуля» и не слал его в канал без реальной причины. Отправка в канал дополнительно ограничена окном `TRAFFIC_HOUR_FROM`..`TRAFFIC_HOUR_TO` (по умолчанию 7–19 по местному времени): изменение вне окна всё равно сохраняется (в памяти и в файле), чтобы не разослать его задним числом при следующей проверке, но в канал не уходит. `_in_broadcast_window()` понимает и окно, переходящее через полночь (`hour_to < hour_from`, например `22–6` или `7–0`), как «с hour_from до конца суток ИЛИ с начала суток до hour_to» — та же функция один в один продублирована в `core/versions.py`.
- `core/currency.py` — команда `/rate` (алиас `/kurs`), курсы USD/EUR/CNY к рублю из официального XML ЦБ РФ (`XML_daily.asp`, windows-1251). Делает два запроса: текущий курс и курс за день до его даты (ЦБ на дату без публикации отдаёт ближайшую предыдущую) — из разницы считается изменение. Результат кэшируется на 30 минут, т.к. ЦБ публикует курс раз в рабочий день.
- `core/moon.py` — команда `/moon` (алиас `/luna`): фаза Луны, освещённость, возраст, восход/заход, ближайшие полнолуние и новолуние. Единственный модуль без сети — данные не запрашиваются, а считаются по алгоритмам Мёуса («Astronomical Algorithms»): гл. 47 (усечённые ряды ELP-2000/82, положение Луны), гл. 25 (Солнце), гл. 48 (освещённость), гл. 49 (моменты сизигий), гл. 12 (звёздное время). Эфемерида детерминирована — внешний источник тут только добавил бы точку отказа, ключи и лимиты; модуль работает при оборванном интернете. Расчёт сверен с эталонными примерами Мёуса (47.a, 48.a, 49.a, 12.a/12.b) и с API Морской обсерватории США (`aa.usno.navy.mil/api/rstt/oneday`): восход/заход совпадают до минуты, освещённость — до процента. Фаза именуется по освещённости, а не по возрасту: восемь равных секторов по 1/8 лунации растягивают «четверть» на ±1.8 суток и подписывают ею диск, освещённый на две трети. Восход/заход ищутся сканированием местных суток с шагом 10 минут — в отдельные дни восхода или захода нет (Луна смещается на ~50 мин/сут), тогда выводится прочерк. `get_moon()` объявлена `async` только ради единообразия с остальными источниками, сети внутри нет.
- `core/mercury.py` — команда `/mercury` (алиасы `/merc`, `/retro`): идёт ли ретрограда Меркурия и когда ближайшая. Второй модуль без сети, но устроен иначе, чем `core/moon.py`: не расчёт на месте, а **захардкоженная таблица** `_RETRO_INTERVALS` — 47 интервалов на 2026–2040, моменты станций в UTC с точностью до минуты. Причина в частоте события: Меркурий ретрограден трижды в год, поэтому 15 лет укладываются в 47 строк исходника — меньше, чем занял бы код, считающий положение Меркурия по VSOP87. Ретрограда определяется кинематически: геоцентрическая эклиптическая долгота убывает, а моменты станций — нули её производной. Таблица сгенерирована из эфемерид JPL Horizons скриптом `scripts/gen_mercury_table.py` (`python scripts/gen_mercury_table.py 2026 2040` печатает готовый литерал для вставки в модуль) — он берёт λ(t) с шагом 1 час и уточняет нуль скорости линейной интерполяцией, что даёт точность порядка секунд. За пределами покрытого таблицей периода модуль не экстраполирует, а возвращает текст «данные кончились, обновить: scripts/gen_mercury_table.py» (`get_mercury_info()` в этом случае бросает `LookupError`). Публичные API вроде `mercuryretrogradeapi.com` не используются сознательно: они отвечают с разрешением в сутки и в половине станций 2026 года расходятся с эфемеридами на целый день. Часовой пояс вывода — `config["mercury"]["timezone_offset_hours"]` из общего `WEATHER_TIMEZONE_OFFSET`; координаты не нужны — ретрограда видна одинаково со всей Земли.
- `core/versions.py` — команда `/ver` (алиасы `/version`, `/versions`): последние **опубликованные в интернете** версии, а не то, что залито в устройство бота. Ответ — по строке на источник, **без значков и без обращения `@[отправитель]`** (команда в `UNADDRESSED_COMMANDS` в `core/commands.py`; `bot.py` по `is_unaddressed()` передаёт в `split_msg()` пустого адресата) — иначе пять строк не влезают в одно сообщение. Пять источников опрашиваются параллельно через `asyncio.gather(..., return_exceptions=True)` — падение одного не роняет ответ целиком, в его строке будет «ошибка запроса», и при неполном результате кэш не записывается. Источники: (1) прошивка MeshCore — релизы GitHub `meshcore-dev/MeshCore` (репозиторий переехал с `ripplebiz/MeshCore`); теги ролей узла (`companion-v`, `repeater-v`, `room-server-v`) выпускаются отдельно, поэтому берётся свежий релиз по каждому префиксу и, если версии совпадают (обычный случай), выводится одной строкой; (2) прошивка `IoTThinks/EasySkyMesh` — сторонняя энергосберегающая сборка, версионируется не семвером, а тегами `PowerSaving17.1` (в выводе сокращается до `PS 17.1`); (3) официальное приложение MeshCore Liam Cottle — из его CHANGELOG (`app.meshcore.nz/assets/CHANGELOG.md`), того же файла, что показывает веб-версия приложения; заголовки вида `## v1.50.0 - 25/September/2026` разбираются регуляркой `_CHANGELOG_HEADING`, месяц — по собственному словарю `_MONTHS` (не через `strptime("%B")`, который зависит от локали процесса), а свежая версия выбирается по номеру версии (`max()` по кортежу чисел), а не по первой записи в файле; сборки для всех платформ нумеруются синхронно, поэтому одна версия описывает приложение в целом; (4) приложение `cm4ker/ommesh` (до сентября 2026 — `cm4ker/meshnet`) — все его релизы помечены prerelease (стабильных нет, из-за чего `releases/latest` отдаёт 404), поэтому для него фильтр prerelease отключён; префикс ветки `dev-` из тега срезается; (5) прошивка YaziFW — сторонняя сборка `YaziAranea/MeshCore` (Smart UI), версия из тега с отрезанным префиксом `smartui-` (`smartui-0.06-test.2` → `0.06-test.2`), а не из названия релиза: названия отстают от тегов (тег `smartui-0.06` назван «Smart UI 0.04»). Для EasySkyMesh, Ommesh и YaziFW свежайший релиз выбирается общим `_latest_release()` **по `published_at`**, а не как первый в списке: порядок списка релизов GitHub не хронологический — у Ommesh сборки 100+ стоят в нём ниже `dev.99`, и логика «берём первый» на этом застревала. Запрашивается страница максимального размера (`per_page=100`), выбор — по самой поздней дате публикации среди подходящих (не draft). Подписи в ответе намеренно короткие и без заголовка: строки с датами иначе не влезают в одно сообщение (лимит 130 байт в каналах; сейчас ответ ~114 байт). Кэш 6 часов — у GitHub API без токена лимит 60 запросов в час на IP, а `/ver` дёргает его четырьмя запросами за вызов. Реестр `SOURCES: dict[ключ -> (значок, имя, функция)]` — единая точка, через которую работают и `/ver` (порядок строк — порядок реестра, имя без значка), и рассылка (подпись со значком, `_source_label()`); новый источник добавляется одной строкой в реестр — интервал `VERSIONS_<КЛЮЧ>_INTERVAL`, файл состояния и `VERSIONS_ANNOUNCE_ON_START` подхватываются по ключу сами; ключ источника попадает в имя env-переменной интервала и в имя файла состояния, поэтому переименование ключа сбрасывает сохранённое состояние рассылки.

  Там же `versions_broadcast_scheduler()` — автоматическая рассылка новых релизов, по образцу `traffic_broadcast_scheduler()` (крутится через `asyncio.gather()` в `main()`, стартует с задержкой 5 c, последнее разосланное значение дублируется в файл `versions_last_<ключ>.txt`, не в git — см. `.gitignore`). Каждый из пяти источников проверяется **своей независимой корутиной со своим интервалом** `VERSIONS_<КЛЮЧ>_INTERVAL` — число с суффиксом `m` (минуты), `h` (часы) или `d` (сутки): `30m`, `2h`, `3d`. Разбирается в `bot.py::_parse_interval_seconds()`, по конфигу передаётся уже в секундах (`interval_seconds`), в логах печатается обратно по-человечески (`_humanize_interval()`). Число без суффикса понимается как часы, и старое имя `VERSIONS_<КЛЮЧ>_INTERVAL_HOURS` тоже ещё читается — чтобы не ломать уже настроенные `.env`. По умолчанию `24h`; `0` отключает конкретный источник; отрицательное и нечитаемое значение — ошибка конфигурации, подменяется умолчанием с предупреждением. Канал `VERSIONS_CHANNEL_IDX` и окно тишины `VERSIONS_HOUR_FROM`..`VERSIONS_HOUR_TO` (по умолчанию 7–19) общие на все источники. Два отличия от пробок, оба из-за редкости события (релиз раз в недели): интервал в часах, а не в минутах; и изменение, случившееся вне окна тишины, **не теряется, а откладывается** — файл состояния обновляется только после фактической отправки, поэтому на следующей проверке изменение обнаружится снова (у пробок наоборот: значение сохраняется и в канал не идёт вовсе). Первый запуск без файла состояния запоминает текущие версии молча — иначе бот разослал бы как «новинку» релиз, вышедший задолго до него. Ошибка запроса к источнику тоже не трогает состояние: версия будет перепроверена в следующий раз.

  Необязательный второй канал `VERSIONS_LINK_CHANNEL_IDX` (не задан — не используется): через `_LINK_PAUSE_SECONDS` (5 c, `asyncio.sleep`) после основного канала туда уходит сообщение `🆕 <источник> <версия> <дата> <ссылка>` — без «было» (`_link_messages()`). Ссылка сокращается (`_shorten_url()`, кэш успешных сокращений в памяти процесса) — чтобы всё ушло одним пакетом: два сообщения подряд в эфир доходят не всегда. Сокращатели перечислены в `_SHORTENERS` и пробуются по порядку до первого успешного: v.gd, затем da.gd (`https://da.gd/s?url=…`, отвечает короткой ссылкой текстом). Если не сработал ни один, текст уходит без ссылки, а полная ссылка — вторым сообщением ещё через 5 c. v.gd (и is.gd того же автора) сообщает об ошибке текстом `Error...` и при HTTP 200 (наблюдалось «database insert failed» — новые ссылки не создавались, уже существующие отдавались), поэтому успех проверяется по префиксу `https://v.gd/` в ответе. Ссылку отдаёт сама функция источника третьим элементом кортежа `(версия, дата, ссылка)`: для GitHub-источников это `html_url` найденного релиза, для приложения MeshCore — константа `_APP_DOWNLOAD_URL` (Google Play), релизов на GitHub у него нет. Если второй канал совпадает с основным, туда уходят только сообщения для канала ссылок (без «было»), а обычное сообщение — нет. Отправка во второй канал идёт уже после сохранения состояния: если она не удалась, её не повторяют, иначе основной канал получил бы дубль. Каждое сообщение в канал ссылок (`_send_until_heard()`) проверяется на эхо: на время отправки модуль сам подписывается на `RX_LOG_DATA` и ждёт `_ECHO_WAIT_SECONDS` (6 c: по логам эхо приходит через 2.6–3.9 с), пока нода не услышит ретрансляцию своего пакета (тот же текст и `sender_timestamp`, непустой путь — своя передача в RX_LOG не попадает). Нет эха — одна переотправка (`_ECHO_RETRIES`) с новой меткой времени: с прежней пакет дал бы тот же хэш, и ретрансляторы отбросили бы его как уже пересланный. Отсутствие эха не доказывает недоставку (нода могла не услышать ретрансляцию), поэтому повтор один — иначе дубли в канале. В случае совпадения каналов первое сообщение уходит как основное и эту проверку не проходит.

  Для проверки того, что приходит в каналы, — `VERSIONS_ANNOUNCE_ON_START` (ключи источников через запятую, например `ommesh`; неизвестный ключ — предупреждение): первая проверка каждой сессии (в том числе после переподключения) для этих источников идёт с `announce=True`: сначала обычная логика рассылки (`_apply_version()`), затем, если версия в канал ссылок ещё не ушла, туда безусловно — мимо проверок «не изменилась», «первый запуск» и окна тишины — отправляется `📌 <источник> <версия> <дата> <ссылка>` (по тем же правилам сокращения). Только в канал `VERSIONS_LINK_CHANNEL_IDX` (не задан — предупреждение, ничего не шлётся): основной канал и файл состояния анонс не трогает, иначе настоящая новая версия, найденная при старте вне окна, так и не дошла бы до основного канала.

  «Отложено до окна» само по себе не гарантирует, что версия когда-нибудь уйдёт: `_source_scheduler()` спит фиксированный `interval_seconds`, поэтому при отложенной версии момент следующей проверки приходится каждый раз на одно и то же время суток — если это время вне окна, оно так и остаётся вне окна навсегда, независимо от того, сколько раз окно успело открыться и закрыться (баг, воспроизведённый на интервале `24h` и окне `7–23`: старт вне окна фиксирует фазу проверок на этом часе — версия так и не уходит). Поэтому вдобавок к обычному сну есть будильник на каждое открытие окна (`hour_from:00`, считает `_seconds_until_hour()`); `_source_scheduler()` ждёт `asyncio.wait({interval_sleep, window_sleep}, FIRST_COMPLETED)` и, если проснулся будильник окна, форсирует внеочередную проверку (`force=True` в `_check_version_change()`) — но только если с последней **фактической отправки** (`last_sent_at`, второй строкой в файле состояния рядом с версией; старые файлы без неё читаются как `None`) прошло не меньше `interval_seconds`. Условие на срабатывание будильника — `if window_sleep in done`, не эксклюзивно («и не interval_sleep»): когда `interval_seconds` кратен суткам, оба будильника с некоторого момента совпадают по фазе и завершаются в один и тот же тик event loop, `interval_sleep` при этом тоже попадает в `done` — эксклюзивное условие с этого момента никогда не срабатывало бы, и баг вернулся бы для самого частого случая (`24h`, `Nd`). Смысл при этом смещается: это уже не «опрашивать источник раз в N», а «не давать окну без рассылки растянуться дольше N».
- `core/contacts.py` — контакты на ноде. Добавляет их сама прошивка по услышанным advert'ам, бот только настраивает её и следит. Семантика взята из исходников прошивки (`examples/companion_radio/MyMesh.cpp`, `src/helpers/BaseChatMesh.cpp`): `manual_add_contacts=1` значит не «ничего не добавлять», а «добавлять только типы, отмеченные битами `autoadd_config`» (0x02 companion, 0x04 repeater, 0x08 room server, 0x10 sensor); бит 0x01 `overwrite_oldest` — при заполненной таблице вытеснять не избранный контакт с самым старым `lastmod` (приходит `CONTACT_DELETED` с pubkey), без него новый узел просто не сохраняется (приходит `CONTACTS_FULL` без данных, какой узел не влез — видно по предшествующему `NEW_CONTACT`). Эти два события взаимоисключающие. `flags & 0x01` у контакта — «избранный». (1) `ensure_auto_add_contacts()` при каждом старте сессии логирует обе настройки и, если `manual_add_contacts` включён, выключает его (`set_manual_add_contacts(False)`, затем перечитывает через `send_appstart()`); `overwrite_oldest` не трогает. (2) `subscribe_contact_events()` логирует добавление контакта, `CONTACTS_FULL` и `CONTACT_DELETED`. Сохранённый новый узел прошивка сообщает не `NEW_CONTACT` (он — только для **не** сохранённых: manual-режим, лимит хопов, полная таблица), а обычным `ADVERTISEMENT` с одним pubkey, как и для известного; библиотека по нему дочитывает изменённые контакты (`get_contacts(lastmod)`), и новый виден только в событии `CONTACTS` как ключ, которого ещё нет в `mc.contacts` (обработчик синхронный — диспетчер вызывает его раньше асинхронного обработчика библиотеки, пополняющего `mc.contacts`; первое `CONTACTS` сессии — начальная загрузка, пропускается); вытесненный контакт убирается из `mc.contacts` вручную — библиотека это событие не обрабатывает, а инкрементальная синхронизация по `lastmod` удалений не видит. (3) `contacts_cleanup_scheduler()` (в `asyncio.gather()` в `run_bot()`, старт через 5 с) удаляет контакты, не слышанные дольше `CONTACTS_MAX_AGE_DAYS` (по умолчанию 30), при старте сессии и затем раз в `CONTACTS_CLEANUP_INTERVAL` (`30m`/`2h`/`7d`, по умолчанию `7d`); `0` в любом из них отключает чистку. Избранные не удаляются. Список берётся с ноды заново (`get_contacts()` с `lastmod=0`), а не из `mc.contacts` — туда не доходят удаления, сделанные из приложения. «Не слышан» = `max(last_advert, lastmod)` старше порога, причём метка дальше суток в будущем в `max()` не участвует (у узлов со сбитыми часами `last_advert` бывает 2035–2037 годом, и такой контакт иначе считался бы живым вечно; если в будущем обе метки — контакт пропускается с предупреждением): `last_advert` — метка по часам отправителя, `lastmod` — по часам нашей ноды (обновляется на advert, сообщение, смену маршрута); часы ноды без RTC после перезагрузки отстают, пока время никто не выставит (бот выставляет его при старте сессии, см. `sync_device_clock()`, но прошивка переводит часы только вперёд — убежавшие вперёд так и останутся), поэтому одной `lastmod` верить нельзя — расхождение часов ноды с компьютером больше часа пишется в лог предупреждением. Состояние чистки в файл не сохраняется: после переподключения чистка идёт снова.
- `scripts/examples.py` — устаревший пример расширения бота, ссылается на класс `MeshCoreBot`, которого в текущей архитектуре (функциональной, через `dispatch`) больше не существует. Не использовать как образец для новых команд — ориентироваться на `core/commands.py`.
- `scripts/fix_node_clock.py` — ручное исправление убежавших вперёд часов ноды (запускать при остановленном боте: без `--apply` только показывает опережение). У ProMicro nRF52840 в прошивке `USE_LFRC` — часы идут от RC-генератора и спешат на минуты в сутки, а `sync_device_clock()` переводит их только вперёд. Обход: сдвинуть назад `lastmod` контактов, у которых он в будущем (`CMD_ADD_UPDATE_CONTACT` принимает `lastmod` необязательным хвостом кадра — библиотека его не передаёт, скрипт дописывает), и сразу перезагрузить ноду — при загрузке прошивка берёт время из `max(lastmod)` и оказывается не впереди, после чего время выставляется точно. Резервная копия контактов пишется в `contacts_backup_*.json` в текущую папку (не в git).
- `scripts/check_flood_scope.py`, `scripts/probe_jams.py`, `scripts/probe_traffic.py`, `scripts/check_methods.py` — разовые скрипты для проб API устройства/сторонних сайтов.
